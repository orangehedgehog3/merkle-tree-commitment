# 随机化 Merkle Tree Commitment 方案

**承诺是先固定内容，再允许别人验证内容。** 承诺方先发布一个短摘要，之后交出消息和验证材料，这个过程叫“开封”。方案需要同时满足两个目标：binding（绑定性）让承诺方不能事后改口，hiding（隐藏性）让别人不能从承诺中猜出尚未公开的消息。

本方案承诺一组按顺序排列的消息。它用 Merkle 树把多个消息摘要合成一个树根，因此既能开封全部消息，也能只开封某个位置。每个位置配一个独立的 32 字节随机值，底层哈希为手写 SHA3-256。

**哈希**把任意长度的字节串变成固定长度的摘要；本方案的摘要为 32 字节。同一输入总会得到同一摘要。Merkle 树的真实叶子保存各条消息的摘要，内部节点保存左右两个子摘要合并后的摘要。

## 从三个消息看完整流程

假设承诺方要固定三个消息：位置 0 是“6”，位置 1 是“9”，位置 2 是“0”。索引从 0 开始；相同内容出现在不同位置时，也可以分别验证。

- **发布承诺。** 承诺方为三个位置分别生成随机值，将消息和随机值做成叶子摘要，再逐层合并。最后公开消息数量 3 和承诺摘要 C，自己保存消息、随机值和树。
- **开封位置 2。** 承诺方交出“0”、位置 2 的随机值，以及从这个叶子走到根所需的兄弟摘要。
- **验证开封。** 验证者用这些材料重算承诺，与之前保存的 C 比较。匹配说明这个位置的消息与原承诺一致。

三个叶子无法在每一层都两两配对，因此补一个占位叶 P₃。下面用 L₀、L₁、L₂ 表示三个真实叶子，用 A₀、A₁ 表示它们的父节点，T 表示树根。最终承诺 C 还将真实数量 3 与 T 一起哈希。

![三个消息的树结构，以及开封位置 2 时的证明路径](assets/merkle-proof.svg)

图中橙色节点是证明提供的摘要：P₃ 和 A₀。验证者先重算 L₂，与右边的 P₃ 合成 A₁，再与左边的 A₀ 合成 T，最后得到 C。**认证路径**就是这样一串从叶子到根的兄弟摘要；它让验证者不必取得整棵树。验证者收到位置 2 的随机值，其他位置的随机值仍由承诺方保存。

> 验证者比较的是此前保存的承诺。这个时间顺序让验证能够说明“内容与之前一致”。完整开封则交出全部消息和随机值，供验证者重建整棵树。

## 设计选择与精确定义

**按位置承诺。** 输入是非空的有序消息列表，真实消息数量记为 n。消息在内部表示为字节串；字符串先按 UTF-8 编码，同编码的字符串和字节串表示同一消息。索引从 0 开始，数量和索引使用 8 字节无符号整数。

**每个叶子独立随机化。** 如果公开的叶子摘要直接来自“0”到“9”，攻击者只需算十次就能比对候选；公开的固定盐也能被加入候选计算。本方案每次承诺都通过 `secrets.token_bytes` 从操作系统取得新的随机字节，为每个位置生成独立的 32 字节随机值。单项开封只公开该位置的随机值。

**让每种哈希输入有明确的解释。** 不同类型使用不同前缀，消息带上数量、索引和长度。这样既能确定字段边界，又能把内容与位置、数量一起绑定。这个做法叫域分隔；其原则可参考 [RFC 9162 的 Merkle 树定义](https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1)，下表规定本方案自己的输入格式。

H 表示手写 SHA3-256，U64 表示 8 字节大端编码，即高位字节在前。以下字段按顺序拼接，再交给 H。前缀 0x00 等均为**一个字节**；摘要使用原始 32 字节，不使用十六进制文本参与计算。mᵢ 是位置 i 的消息，rᵢ 是它的随机值，|mᵢ| 是消息的字节数。

| 节点或输出 | 交给 H 的字段 |
| --- | --- |
| 真实叶子 Lᵢ | 0x00 ‖ U64(n) ‖ U64(i) ‖ U64(\|mᵢ\|) ‖ mᵢ ‖ rᵢ |
| 占位叶 Pᵢ | 0x02 ‖ U64(n) ‖ U64(i) |
| 内部节点 | 0x01 ‖ 左摘要 ‖ 右摘要 |
| 最终承诺摘要 C | 0x03 ‖ U64(n) ‖ 树根 T |

消息长度确定消息结束的位置，后面的 32 字节就是随机值。左右子节点的顺序固定，换序会改变哈希输入。

**补齐规则。** N 是不小于 n 的最小二次幂。例如 n=3 时 N=4；索引 n 到 N−1 填占位叶，只有索引小于 n 的真实叶子接受开封。所有路径深度相同，记为 h=log₂N。补齐增加了节点，但 N 满足 n≤N<2n，所以建树的哈希工作量仍随消息数量线性增长。

**公开信息与私有状态。** 公开承诺包含版本、n 和 C；承诺方保存全部消息、随机值和各层摘要。单项开封交出消息、索引、该位置的随机值及 h 个兄弟摘要。完整开封交出全部消息与随机值。当前版本不接收空列表；空字节消息是合法消息。字符串不做 Unicode 归一化。

## 开封如何验证

单项验证先读取承诺和证明，检查版本、字段大小、期望索引和路径长度。索引必须小于 n，路径必须恰好有 h 个兄弟摘要。随后按前文例子重算叶子、父节点、树根和 C。当前节点处于偶数位置时在左边，处于奇数位置时在右边；到上一层后，位置除以 2 取整数商。

完整验证先确认消息与随机值的数量一致，并与公开的 n 相同，再按相同规则重建全部节点。两种验证都与保存的 C 比较，匹配返回 True；内容不符或格式不对返回 False。单独使用二进制解析器时，错误编码会抛出 ValueError。

## 批量开封与批量验证：核心设计亮点

> 本方案把“同时证明多个叶子”作为一等设计，而不是附带优化。真正的目标不是让多证明看起来像多个单项证明拼在一起，而是让它们共享同一条路径，尽可能重复利用已经计算过的祖先节点。

**批量开封与批量验证**的核心思想是：对多个叶子位置同时证明时，若它们在某一层共享同一个兄弟或祖先路径，就不必重复发送同一份摘要。对于一个活动集合，我们沿着树自底向上合并：

- 若一个位置的兄弟也在当前集合中，则这两个子节点可以合并为更高一层的父节点；
- 若该兄弟不在集合中，则它必须作为 frontier 的一个节点被单独包含在证明中；
- 逐层向根收敛，最后得到的就是去重后的 frontier。

这意味着多位置证明的大小并不随“个数 × 单路径长度”线性增长，而是更接近“共享部分被压缩后的唯一节点数”。索引按升序编码，验证者可根据深度和位置信息恢复 frontier 的布局顺序。

`open_many(indices)` 返回按索引升序排列的消息和 `MultiProof`；证明包含索引、对应随机值和 frontier 摘要，不包含消息本身。`verify_many()` 的过程与此相反：它先对每个已开封叶子做 `H(leaf)`，然后在每一层按活动集合重建父节点；若某一侧父节点来自已计算过的内部节点，则直接复用；若需要的兄弟来自 frontier，则从证明中读出该摘要并继续向上合并，最后与公开承诺中的 `root` 绑定，验证 `C = H(0x03 || U64(n) || T)` 是否一致。

**收益非常明显：** 若分开验证 k 个位置，逐项单项验证大约需要 `k(h+2)` 次哈希；而批量验证只需要接近 `k + q + 1` 次哈希，其中 q 是去重后的 frontier 中唯一父节点数。相邻叶子通常共享大量低层祖先，因此 q 很小；随机或分散叶子虽然 q 会增大，但仍远优于简单重复发送每个叶子对应的完整路径。换言之，批量验证的真正价值在于：它把一次性增加的“验证集合”转化成了“共享路径的重用”，从而同时降低了传输量和验证成本。

这也是 `MultiProof` 的核心意义：不仅是一个能“开多个位置”的接口，而是一个把重复路径压缩成共享前沿节点的设计。对于大规模批量证明场景，它是整个方案的主要效率增益来源之一。

版本固定为 1。编码字段的顺序和大小如下；解析器检查截断、额外字节和版本，单项证明最多 64 层。

| 对象 | 编码内容 | 编码大小 |
| --- | --- | --- |
| 公开承诺 | 1 B 版本、8 B 数量、32 B 摘要 | 41 B |
| 单项证明 | 1 B 版本、8 B 索引、32 B 随机值、2 B 大端路径层数、每层 32 B 兄弟摘要 | 43 + 32h B |
| 批量证明 | 1 B 版本、8 B 开封数量；每项 8 B 索引和 32 B 随机值；8 B frontier 数量及每个 32 B 摘要 | 17 + 40k + 32s B |
| 完整开封 | 1 B 版本、8 B 数量；每项为 8 B 长度、消息、32 B 随机值 | 9 + Σ(40 + 消息字节数) B |

其中 k 是开封位置数，s 是去重后的 frontier 摘要数。前文三个消息的例子有两层路径，单项证明为 107 B。**消息本身不计入证明大小**，它是验证的单独输入；计算整个开封的传输量时，还要计入消息及应用层的长度编码。

## 安全性分析

### Binding：为什么承诺方不能改口

如果把位置 2 的“0”改成“1”，真实叶子的哈希输入就变了。想让改后的开封仍对应同一个 C，就必须在某一层让两个不同输入得到同一个摘要。这样的输入对叫**哈希碰撞**；抗碰撞性要求攻击者难以找到它。

本方案的 binding 以 SHA3-256 抗碰撞为假设。精确目标是：同一个公开承诺不能接受两个消息向量不同的完整开封；同一个承诺和同一个索引也不能接受两条消息不同的单项开封。攻击者可以任意选择自己的随机值，绑定仍应成立。

- 数量不同的完整开封会被公开数量检查拒绝。数量还写入最终哈希输入，因此固定 C 后改变 n，也会给出一次碰撞。
- 数量相同而某条消息不同，两份开封的叶子输入不同。如果叶子摘要相同，这就是碰撞；如果叶子摘要不同，就沿路径向上找第一次汇合处。那里不同的子节点对产生了同一个父摘要，也构成碰撞。如果直到树根都不同而 C 相同，则碰撞出现在最终承诺哈希。
- 同索引的两份单项开封沿相同深度和左右规则计算，并匹配同一个 C。消息不同意味着叶子输入不同；同样沿两条计算路径找第一次汇合处，就能得到碰撞。

这种“从成功改口构造哈希碰撞”的推理叫安全归约。字段能唯一解析、四类节点使用不同前缀、数量与位置固定，是这个推理成立的前提。因此，重排、删增消息以及把证明移到另一个位置都属于绑定目标。SHA3-256 的通用碰撞攻击工作量约为 2¹²⁸ 次。

### Hiding：为什么低熵消息也能隐藏

猜测位置 2 的消息可能只有十个候选，但计算其真实叶子摘要还需要 r₂。开封另一个位置给出的随机值不能替代 r₂，因为每个位置都独立生成随机值。即使证明公开了一个未开封叶子的摘要，攻击者仍需要猜中该叶子的随机值，才能用正确输入比对消息。

这里的 hiding 在**随机预言机模型**中分析：把 H 看成一张随机生成的查找表，新输入得到独立均匀的 256 bit 输出，相同输入仍返回相同输出。实现选用 SHA3-256 来实例化 H。这个模型和独立均匀的 32 字节随机值，是以下论证的假设；抗碰撞性本身不足以推出隐藏性。

安全实验让攻击者先给出两个数量相同的消息列表。挑战者随机选其中一个，生成所有随机值并返回承诺。攻击者猜选了哪一个；方案希望它相对于随机猜测的优势可以忽略。只比较相同数量，是因为 n 本来就公开。

只要攻击者还没有查询隐藏叶子的真实输入，该叶子摘要就可视为与消息无关的随机值。两个实验可以为对应叶子分配同样的随机摘要，后续树计算也就产生相同的公开视图。使这份对应关系失效的关键事件，是攻击者猜中未知随机值并查询真实叶子输入。

设 q 是攻击者的哈希查询次数，n 是真实叶子数量。一次针对某个未知随机值的猜测命中概率为 1/2²⁵⁶。把两组挑战实验、最多 n 个隐藏位置和 q 次查询的命中事件合起来，得到系数 2nq；用保守的上界估计：

$$
\Pr[\text{命中隐藏叶子输入}] \leq \frac{2nq}{2^{256}}.
$$

在这个事件发生前，两组公开视图可按前述方式对应；多项式数量的叶子和查询下，区分优势可忽略。这个上界解释随机值如何支持隐藏性，整体安全强度仍要同时考虑 binding 的碰撞界。

**部分开封。** 若事先固定要开封的位置集合，让两个挑战列表在这些位置上的消息相同，则公开这些消息、随机值和路径后，未开封位置仍有独立的未知随机值，可以应用同样的查询命中论证。实现支持按需多次开封；这里给出的证明范围是固定集合部分开封。

> n、开封索引和已开消息公开；完整开封公开全部内容。已开消息与其他消息的外部相关性仍可能带来推断。一般自适应选择性开封、随机源失效、私有状态泄露和侧信道不属于这里的证明范围。

## 手写 SHA3-256 怎样计算

SHA3-256 在内部维护 25 个格子，每格是 64 位整数，初始全为零，共 200 B。格子排成 5 列、5 行，代码用 `state[x][y]` 表示列 x、行 y。编号为 x+5y：先走完一行，再走下一行。每个整数按小端字节序读取和写出，即低位字节排在前。

消息每 136 B 分一块，依次混入状态的前 17 个格子；这部分叫吸收率（rate）。剩余 64 B 不直接异或消息，叫容量（capacity），也会参加每次状态混合。

![SHA3-256 从消息块到摘要的计算流程](assets/sha3-flow.svg)

**先补齐消息。** 实现追加后缀 0x06，补零到 136 B 的整数倍，再把末字节最高位设为 1，即与 0x80 合并。如果消息在块内已占 135 B，后缀正好位于块末，得到 0x86；如果消息恰好占满 136 B，就再加一个填充块。本方案使用 FIPS 202 的 SHA3-256，通常称为 Keccak-256 的实例使用不同后缀。

**每块做 24 轮混合。** 这套状态变换叫 Keccak-f[1600]；1600 是状态的位数。每轮的五个步骤分别改变以下关系：

| 步骤 | 做什么 |
| --- | --- |
| θ | 求各列的异或值，将相邻列的信息混入当前列 |
| ρ | 在每个格子内部循环移动位 |
| π | 将整个格子移动到新坐标 |
| χ | 用同一行相邻格子的位，决定当前格子哪些位翻转 |
| ι | 将本轮常数异或到 (0,0) 格子 |

Python 整数可以超过 64 位，循环移位和取反运算通过掩码保留需要的 64 位。所有块吸收完毕后，按原来的格子顺序写回字节，取前 32 B 作为摘要。

消息的字节数除以 136，取整数商再加 1，就是本实现的状态置换次数。135 B 消息只需一次置换，136 B 消息需要两次，这也解释了性能表中这个边界附近的耗时变化。真实叶子输入有 57 B 固定开销，内部节点输入固定 65 B，最终承诺输入固定 41 B；所以哈希调用次数相同，长消息仍可能花更多时间。[FIPS 202](https://csrc.nist.gov/pubs/fips/202/final) 给出算法规范和安全工作量说明。

## 正确性验证与性能评估

SHA3 测试使用 [NIST CAVP 的字节测试向量](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Algorithm-Validation-Program/documents/sha3/sha-3bytetestvectors.zip)：0–136 B 的全部 137 条 ShortMsg，以及 273、410、4109 B 的三条 LongMsg，共 140 条，另加 abc 固定示例。消息和期望摘要保存在 `tests/data/sha3_vectors.json`，运行时只计算本项目的手写哈希。

协议测试从正常开封和错误开封两方面核对实现。正常情况包含单叶、非二次幂、重复值、空消息和 Unicode；错误情况包含消息、随机值、兄弟摘要、索引、数量及根的篡改。独立递归规格检查树计算，固定字节样例检查 v1 编码，解析测试检查截断、尾随字节和字段类型。

补齐到 N 个叶子后，建树共调用 H 2N 次：N 个真实或占位叶、N−1 个内部节点、一次最终承诺。单项验证调用 h+2 次哈希，证明包含 h 个兄弟摘要。因此固定消息长度时，建树与完整验证为 O(n)，证明生成与单项验证为 O(log n)。消息变长还会增加哈希吸收的块数；私有状态存储为 O(n+总消息字节数)。

[性能报告](../results/性能与验证结果.md) 给出 32 B 消息下的规模测量、消息长度实验和单次哈希实验，包含五组样本的均值、标准差及测量边界。现有数据来自重构前提交 `2ff13ad`，作为历史基线保留；它不是当前版本的重新测量。原始样本和执行输出分别在 `results/results.json`、`results/run.log`，路径相对于仓库根目录。
